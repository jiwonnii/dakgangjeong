# 외부 API 조사 (2026-08 기준)

Meoksa 산책 코스 추천에 쓸 수 있는 외부 데이터 정리.
각 항목의 "확인 필요" 표시는 실제 신청 전 문서를 다시 봐야 하는 부분.

## 1. 핵심 발견

### 1-1. TMAP 보행자 경로 API로 횡단보도·계단을 자동으로 셀 수 있다

응답의 각 구간에 `facilityType` 코드가 붙어 나온다.

| 코드 | 의미 |
|---|---|
| 1 | 교량 |
| 2 | 터널 |
| 3 | 고가도로 |
| 11 | 일반보행자도로 |
| **12** | **육교** |
| **14** | **지하보도** |
| **15** | **횡단보도** |
| 16 | 대형시설물이동통로 |
| **17** | **계단** |

`turnType` 211~217은 횡단보도 방향 안내다.

→ **횡단보도 개수 = `facilityType === 15`인 구간 수.** 손으로 셀 필요 없음.
→ 계단(17)은 노령견·소형견·유모차 동반에 중요한 감점 요소로 쓸 수 있다.

응답 필드 전체: `index`, `pointIndex`, `name`, `description`, `direction`,
`intersectionName`, `nearPoiName`, `nearPoiX/Y`, `turnType`, `pointType`,
`facilityType`, `facilityName`, `totalDistance`, `totalTime`, `lineIndex`,
`roadType`, `categoryRoadType`, `time`, `distance`, `roadName`

엔드포인트: `https://apis.openapi.sk.com/tmap/routes/pedestrian`

### 1-2. TMAP에 자전거 경로안내 API가 있다

TMAP은 자동차 / 보행자 / **자전거** / 타임머신(도착시간 기반) 경로를 모두 제공한다.
카카오모빌리티는 도보 길찾기(Directions)는 있으나 **자전거 API는 미제공**.

**자전거 경로가 산책에 쓸모 있는 이유(가설):**
자전거 경로는 자전거도로를 선호하는데, 국내 자전거도로는 하천변·공원에 몰려 있다.
즉 자전거 경로 ≈ 차 없는 쾌적한 길일 가능성이 높다.
보행자 경로와 자전거 경로를 비교하면 "차도 회피 구간"을 추정할 수 있다.

**단, 양날의 검:** 자전거도로는 자전거가 빠르게 지나다녀서 개에게는 위험할 수도 있다.
가산점이 아니라 별도 지표로 두는 게 안전하다. → 실제 데이터로 검증 필요.

### 1-3. 서울 실시간 도시데이터로 인구 혼잡도를 자동으로 얻을 수 있다

- 서울시 주요 **120개 장소**의 인구·교통·환경·날씨 융합 데이터
- 통신사(KT/SKT) 기지국 기반, **5분 단위** 집계, 50m×50m 격자 분배
- 최근 12시간 혼잡도 + **AI 기반 향후 12시간 예측**

→ `crowd_level`을 수동 입력이 아니라 **실시간 값**으로 대체 가능.
→ 게다가 예측이 있어서 "지금 말고 2시간 뒤에 가세요" 같은 제안도 가능.

**한계:** 120개 주요 장소 한정. 동네 골목은 커버 안 됨.
전국 단위가 필요하면 TMAP "실시간 장소혼잡도" 상품을 봐야 한다(확인 필요).

## 2. API별 정리

### TMAP (SK Open API)

| 기능 | 용도 |
|---|---|
| 보행자 경로안내 | **도보 경로 + 횡단보도/계단 자동 추출** ★ |
| 자전거 경로안내 | 차 없는 길 추정 (가설) |
| 자동차 경로안내 | 미사용 |
| POI 검색 (150만건+) | 주변 공원·시설 검색 |
| 지오코딩 / 역지오코딩 | `region` 자동 채우기 |
| StaticMap | **산책 기록 지도 이미지** (PRD 요구사항) |
| 실시간 교통정보 | 차량 혼잡 |
| 실시간 장소혼잡도 | `crowd_level` 후보 (확인 필요) |
| 다중 경유지 / 경유지 최적화 | 순환 코스 생성에 활용 가능 |

> 무료 한도와 과금 정책은 신청 시 확인 필요.

### Kakao

| 기능 | 용도 |
|---|---|
| 키워드 장소 검색 | **공원 검색은 키워드로 해야 함** |
| 카테고리 장소 검색 | 학교(SC4), 병원(HP8), 지하철(SW8) 등 18종 |
| 좌표→주소 / 주소→좌표 | 지역 판별 |
| Static Map | 지도 이미지 |
| 카카오모빌리티 Directions | 도보 길찾기 (사용 신청 필요) |

**함정:** 카테고리 코드 18종에 **"공원"이 없다.** 큰 공원 일부만 관광명소(AT4)로
잡히고 동네 공원은 키워드 검색으로 찾아야 한다.
**자전거 길찾기 API는 제공하지 않는다** (앱에는 있지만 API 미개방).

### Naver Maps (NCP)

지도 표시 / 지오코딩 / Static Map은 좋으나 **Directions 5는 자동차 전용**.
도보 경로가 없어 우리 용도에는 카카오·TMAP보다 약하다.

### VWorld (국토교통부 공간정보 오픈플랫폼)

- 약 900종 공간정보, **무료**
- 수치표고모델(DEM) 포함 → **경사도** 계산 가능
- 연속지적도 등을 GeoJSON으로 반환 → PostGIS에 바로 투입 가능
- 3D 데이터 API는 종료됨

→ 공원 **폴리곤**을 얻을 수 있으면 `park_ratio` 자동 계산 가능. 확인 필요.

### 공공데이터포털 (data.go.kr)

| 데이터 | 용도 |
|---|---|
| 기상청 단기예보 | 날씨 (※ 위경도 아닌 **격자 nx, ny** 필요 — 변환 공식으로 계산) |
| 기상청 생활기상지수 3.0 | **체감온도 / 자외선지수 / 대기정체지수 / 동파가능지수** ★ |
| 에어코리아 대기오염정보 | PM10, PM2.5, O3, NO2, CO, SO2 |

| 에어코리아 대기오염 예보 | 미세먼지 예보 |
| **전국교통사고다발지역표준데이터** | `risk_zones` 투입 |
| 도로교통공단 보행자 사고다발지역 | 반경 150m 내 3건 이상 지점 TOP3 |

| **전국도시공원정보표준데이터** | 공원 위치 + 면적 (**점 데이터**, 폴리곤 아님) |
| **전국그늘막쉼터표준데이터** | 여름 그늘 |
| **전국무더위쉼터표준데이터** | 폭염 대피 |
| 행정안전부 동물병원 조회서비스 | 응급 상황 대비 |
| 반려동물 동반 가능 문화시설 | 반려견 출입 가능 구간 |

> "표준데이터"는 전국 지자체가 **통일된 형식**으로 제공 → 파싱 로직 하나로 전국 커버.

### OpenStreetMap Overpass API

무료. 태그 기반 질의로 다음을 얻을 수 있다.

- `surface` 태그 → **노면 종류** (asphalt, paving_stones, dirt, ground …)
- `highway` 태그 → 도로 위계 (residential / primary / footway / path)
- `leisure=park` 폴리곤 → **공원 경계** (park_ratio 자동 계산)
- `natural=tree_row`, `barrier` 등 부가 정보

**한계:** 한국 커버리지가 지역마다 들쭉날쭉. 도심은 쓸 만하지만 `surface` 태그
채움률은 낮을 수 있다. **MVP 지역에서 실제 커버리지를 먼저 확인해야 한다.**

도구: Overpass Turbo로 질의를 미리 테스트 가능.

## 2-2. 차량 노출도 집중 조사 (추가)

"차량 노출도"를 직접 주는 API는 **없다.** 골목 단위 실시간 통행량은 국내에 존재하지 않는다.
다만 **여러 데이터를 조합하면 정적(static) 근사치는 자동 계산이 가능하다.**

### 핵심: 국가표준노드링크 (국토교통부, 무료)

전국 도로망을 노드-링크로 표현한 GIS 데이터. 각 링크(도로 구간)의 속성:

| 필드 | 의미 |
|---|---|
| LINK_ID | 링크 식별자 |
| F_NODE / T_NODE | 시작 / 종료 노드 |
| **LANES** | **차로수** ★ |
| **ROAD_RANK** | **도로등급** ★ |
| ROAD_TYPE | 도로유형 |
| ROAD_NO / ROAD_NAME | 도로번호 / 도로명 |
| ROAD_USE | 도로사용여부 |
| **MAX_SPD** | **최고제한속도** ★ |
| REST_VEH / REST_W / REST_H | 통행제한차량 / 하중 / 높이 |

**ROAD_RANK 코드표**

| 코드 | 도로등급 |
|---|---|
| 101 | 고속도로 |
| 102 | 도시고속화도로 |
| 103 | 일반국도 |
| 104 | 특별·광역시도 |
| 105 | 국가지원지방도 |
| 106 | 지방도 |
| 107 | 시군도 |
| 108 | 기타 |

→ **도로등급 + 차로수 + 제한속도 = 차량 노출도 프록시.** 전국 커버, 무료.

### 보조 데이터 (전부 전국 표준데이터, 무료)

| 데이터 | 차량 노출도에 주는 정보 |
|---|---|
| **전국보행자전용도로표준데이터** | 차량 통행 없음 → 노출도 **0** |
| **전국보행자우선도로표준데이터** | 보행자 우선. **사고건수·사망자수·과속방지 시설·도로폭**까지 포함 |
| **전국어린이보호구역표준데이터** | 30km 이하 제한 + 보호구역 도로폭 |
| **전국과속방지턱표준데이터** | 과속방지턱 = 차량 감속 구간 |
| 전국횡단보도표준데이터 | 횡단보도 위치 (TMAP 없이도 확보 가능) |
| 전국도로안전표지표준데이터 | 도로 안전표지 |

### TMAP 보행자 경로 응답에 이미 들어있는 것

`roadType`, `categoryRoadType` 필드가 구간별로 나온다.
즉 **보행자 경로 API 한 번 호출로 횡단보도 개수 + 구간별 도로 유형을 동시에** 얻는다.

### OSM 태그

| 태그 | 의미 |
|---|---|
| `highway=footway` / `pedestrian` / `path` | 보행자 전용 → 노출도 0 |
| `highway=living_street` | 생활도로. 보행자가 차량보다 우선, 20km 이하 |
| `highway=residential` | 주택가 도로. 통과 교통 적음 |
| `highway=tertiary` / `secondary` / `primary` | 위계가 올라갈수록 차량 많음 |
| `maxspeed`, `lanes` | 제한속도, 차로수 |

### 차량 노출도 자동 산출 초안

```
기본값 = ROAD_RANK 기준
  101, 102  → 산책 불가 (후보에서 제외)
  103       → 5.0   일반국도
  104       → 4.0   특별·광역시도
  105, 106  → 3.5   지방도
  107       → 2.5   시군도
  108       → 2.0   기타

보정
  LANES >= 6      → +1.0
  LANES <= 2      → -0.5
  MAX_SPD >= 60   → +1.0
  MAX_SPD <= 30   → -1.0

덮어쓰기 (우선 적용)
  보행자전용도로   → 0.0
  보행자우선도로   → 0.5
  어린이보호구역   → -1.0 보정
  과속방지턱 존재  → -0.5 보정

최종 = clamp(0, 5)
코스 전체 값 = 구간 길이로 가중평균
```

### 끝내 얻을 수 없는 것

| 항목 | 상태 |
|---|---|
| 골목 단위 **실제 통행량(대수)** | ❌ 조사 지점이 간선도로 위주 (도로교통량 통계연보) |
| 골목 **실시간** 소통 | ❌ ITS·TOPIS는 고속도로·국도·간선도로만 (5분 단위) |
| 한국도로공사 교통량 API | ❌ 고속도로 영업소 단위. 산책과 무관 |
| **체감 위험도** (인도 폭, 차 속도, 주차 상태) | ❌ **직접 걸어야만 앎** |

> ⚠️ **확인 필요:** 표준노드링크가 아주 좁은 골목까지 포함하는지는 검증해야 한다.
> 노드링크는 교통정보 교환이 목적이라 관리 대상 도로 위주일 가능성이 있다.
> MVP 지역에서 실제 커버리지를 먼저 확인할 것.

### 결론

**차량 노출도는 "자동 초기값 + 사람 보정" 구조로 가는 게 최선이다.**

1. 표준노드링크 + 보조 데이터로 **자동 초기값** 산출
2. 직접 걸으면서 **실제 체감으로 덮어쓰기**
3. 자동값과 사람값이 크게 다른 구간은 "검증 필요"로 표시 → 데이터 품질 관리

이러면 손으로 넣는 부담이 크게 줄고, 자동값이 있으니 코스를 아직 안 걸어본 지역도
일단 추천은 할 수 있다.

## 2-3. 그늘 계산 — 참고만, MVP에서는 제외

> **결정: 그늘 계산은 MVP 범위에서 제외한다.**
> 아래 내용은 나중에 확장할 때를 위한 참고 자료다.
> 다만 이 조사에서 **가로수 데이터**는 그늘 계산 없이도 쓸 수 있다는 걸 확인했다.
> (→ 2-4 참고)


### 참고 사례: 그늘로 (뚜벅의 여름길)

2026년 여름 화제가 된 앱. 서울대 수학교육과 학생이 **약 2주** 만에 개발, 배포 4일 만에
약 2만 명이 사용. 걸어다니며 그늘을 조사한 게 아니라 **기하학적으로 계산**했다.

**사용한 데이터 조합**
- OpenStreetMap (도로망)
- 국토교통부 건물 형상·높이 정보
- 가로수 위치·수관 정보
- 공원 정보
- 대중교통 정보 (약냉방칸 등)
- 서울시 무더위쉼터

**동작 원리**: 출발 시각의 태양 고도·방위각 + 주변 건물 형상/높이 → 그림자 폴리곤 계산
→ 경로별 그늘 비율 산출 → 최단 경로와 그늘 많은 경로를 함께 제시

### 우리가 그대로 쓸 수 있는 재료

| 재료 | 내용 | 키 필요 |
|---|---|---|
| **SunCalc** | 태양 고도·방위각 계산. Jean Meeus 천문 알고리즘, ±0.01° 정확도 | ❌ 순수 계산 |
| **pg-shadows** | **PostGIS용 그림자 계산 함수** (OSMBuildings) | ❌ SQL 함수 |
| **국토교통부 GIS건물통합정보** | 건물 폴리곤 + 높이. WMS/WFS API 제공 | ✅ |
| **전국GIS건물통합정보표준데이터** | 전국 표준 버전 | ✅ |
| **서울시 가로수 위치정보** | 위경도 + **수고** + **수관너비** + 수종 | ✅ |
| **전국가로수길정보표준데이터** | 전국 가로수길 (시작/종료 좌표, 수종, 수량, 길이) | ✅ |

### pg-shadows 사용법

```sql
-- Shadow(ARRAY[방위각, 고도], 건물폴리곤, 높이) -> 그림자 폴리곤
SELECT ST_AsGeoJSON(Shadow(ARRAY[90, 5], way, 25), 4326)::json AS shadow
FROM planet_osm_polygon
WHERE osm_id = 313670734;
```

방위각·고도는 SunCalc로 미리 계산해서 넣는다. 순수 SQL 함수라 확장 설치 불필요.

**그림자 공식**
```
그림자 길이 = 높이 / tan(태양고도)
그림자 방향 = 태양방위각 + 180°
```

**우리 스택에 그대로 맞는다.** 이미 Supabase Postgres + PostGIS를 쓰고 있고,
`walk_courses.path`가 LineString이므로 `ST_Intersection(경로, 그림자폴리곤)` 으로
**경로의 그늘 비율**을 바로 구할 수 있다.

### 이게 바꾸는 것: 그늘은 상수가 아니라 시간의 함수

기존 설계는 `shade_level 0~5`를 사람이 입력하는 **고정값**이었다.
계산으로 가면 이렇게 바뀐다.

```
같은 코스, 같은 날
  오후 3시 출발 → 그늘 비율 32%
  오후 6시 출발 → 그늘 비율 78%
```

→ **"지금 말고 3시간 뒤에 나가세요"** 같은 시간 추천이 가능해진다.
→ PRD의 "산책 지양 알림"이 단순 경고에서 **대안 제시**로 격상된다.

### 그늘로보다 한 발 더 나갈 수 있는 지점 (차별화)

그늘로는 **사람**을 위한 앱이다. 개는 조건이 다르다.

| 차이 | 의미 |
|---|---|
| **개는 지면에 훨씬 가깝다** | 사람 눈높이 그늘과 지면 그늘이 다르다. 낮은 담장·화단·주차차량 그늘도 개에게는 유효 |
| **발바닥이 노면에 직접 닿는다** | 기온 30℃일 때 직사광 아스팔트 표면은 50~60℃까지 오른다. 화상 위험 |
| **체온 조절이 사람보다 불리하다** | 땀을 흘리지 못하고 헐떡임에 의존 |

→ **그늘 × 노면 종류**를 결합하면 사람용 앱이 못 하는 계산이 된다.
   그늘 없는 아스팔트 = 최악, 그늘 있는 흙길 = 최선.
→ PRD 문제 정의의 **"여름철 노면 열기"** 가 여기서 실제로 구현된다.

### 같은 방식으로 계산 가능한 다른 것

건물 형상·높이 데이터가 확보되면 그늘 외에도 쓸 수 있다.

- **개방감 / 밀폐감** — 건물에 둘러싸인 좁은 골목인지, 트인 길인지
- **야간 체감 안전** — 건물 밀도 + 가로등(보안등 표준데이터) 조합
- **바람길** — 난이도 높음. MVP 범위 밖

## 2-4. 가로수 밀도 — 그늘 계산 없이 바로 쓰는 지표

그늘로가 쓴 데이터 중 **그늘 계산을 하지 않아도 즉시 쓸 수 있는 유일한 재료.**

### 왜 쓸모 있나

- **가로수 많은 길 = 쾌적한 산책로.** 직관적으로도 맞고 계산도 단순하다.
- **반려견 특화 이유:** 가로수는 개가 냄새 맡고 마킹하는 지점이다.
  산책 만족도에 실제로 영향을 준다. 사람용 앱에는 없는 관점.

### 계산 방법 — PostGIS 한 줄

```sql
-- 경로 20m 반경 내 가로수 개수 / 경로 길이(km)
SELECT count(*) / (ST_Length(path::geography) / 1000) AS trees_per_km
FROM street_trees
WHERE ST_DWithin(path::geography, tree_point::geography, 20);
```

태양 위치·그림자 폴리곤이 전혀 필요 없다. 점 개수만 세면 된다.

### 데이터

| 데이터 | 포함 정보 |
|---|---|
| 서울시 가로수 위치정보 | 위경도, 수종, **수고**, **수관너비**, 흉고지름, 관리등급 |
| 전국가로수길정보표준데이터 | 시작/종료 좌표, 수종, 수량, 길이 |

> `수고`·`수관너비`가 이미 들어있으므로, 나중에 그늘 계산을 얹고 싶어지면
> **데이터를 다시 모을 필요 없이 계산 로직만 추가**하면 된다.

### 그늘로가 쓴 나머지 데이터 판정

| 데이터 | 우리 활용도 |
|---|---|
| OpenStreetMap | ⭐ 핵심 (도로 위계 / surface / 공원 폴리곤) |
| **가로수 위치·수관** | ⭐ 밀도 지표로 채택 |
| 공원 정보 | ⭐ 이미 채택 (park_ratio) |
| 건물 형상·높이 | ❌ 그늘 제외 시 활용도 낮음 |
| 대중교통(약냉방칸) | ❌ 산책과 무관 |
| 무더위쉼터 | ❌ 실내 시설이라 반려견 동반 불가한 곳이 대부분 |

## 3. 코스 속성별 자동화 가능 여부 (최종)

| 속성 | 자동화 | 출처 |
|---|---|---|
| path, distance, is_loop, start_point | ✅ 확정 | GPS 기록 |
| **횡단보도 개수** | ✅ 확정 | TMAP `facilityType=15` |
| **계단·육교·지하보도** | ✅ 확정 | TMAP `facilityType=17/12/14` |
| **가로등** | 🟡 유력 | 전국보안등정보표준데이터 |
| **경사도** | 🟡 유력 | VWorld DEM |
| **park_ratio** | 🟡 유력 | OSM `leisure=park` 폴리곤 or VWorld |
| **crowd_level** | 🟡 서울 한정 | 서울 실시간 도시데이터 (120곳) |
| **차량 노출도** | 🟡 **자동 초기값 가능** | 표준노드링크 + 보행자전용/우선도로 + 스쿨존 + 과속방지턱 (2-2 참고) |
| **노면 종류** | 🟠 부분 | OSM `surface` (커버리지 확인 필요) |
| **가로수 밀도** | ✅ 계산 가능 | 가로수 데이터 + PostGIS `ST_DWithin` (2-4 참고) |
| **그늘** | ⏸ MVP 제외 | 계산은 가능하나 범위에서 뺌 (2-3 참고) |
| **개 마주칠 확률** | ❌ 수동 | API 없음. 우리 산책 기록 쌓이면 자동화 |
| **보도 상태** | ❌ 수동 | API 없음 (인도 폭·파손·주차 상태) |
| **음수대** | ❌ 수동 | 일부 지자체만 |

**결론: 차량 노출도는 자동 초기값을 뽑을 수 있게 됐다.**
다만 "인도가 좁다", "차가 실제로 빠르게 지나간다", "불법주차로 시야가 막힌다" 같은
**체감 위험도는 여전히 직접 걸어야만 알 수 있다.**
자동값으로 커버리지를 확보하고, 직접 걸은 곳은 사람 값으로 덮어쓰는 2층 구조가 최선.

## 4. 신청 우선순위

1. **공공데이터포털** — 계정 하나로 기상청·에어코리아·표준데이터 전부 신청 가능. 즉시 신청 권장
2. **TMAP (SK Open API)** — 보행자 경로가 핵심. 횡단보도 자동화가 여기 달림
3. **VWorld** — 무료, 경사도·폴리곤
4. **Kakao** — 지도 표시·장소 검색·Static Map
5. **서울 열린데이터광장** — MVP 지역이 서울로 확정되면
6. OSM Overpass — 키 불필요, 바로 테스트 가능

> 공공데이터포털은 개발계정 / 운영계정이 나뉘고 승인에 시간이 걸릴 수 있다.
> 일 호출 한도(보통 1,000회)가 있으므로 **지역+시간 단위 캐시 필수**.
